# Magpie 参考评估与功能计划

> 评估基线：openllm v0.3.25。
>
> 参照项目：[yetone/magpie](https://github.com/yetone/magpie)，本文分析基于
> commit [`a15e576`](https://github.com/yetone/magpie/tree/a15e576564cb90d4d027e8b8cb7821472de0a3fc)
> 及当时的 README、子系统文档和源码。
>
> 本文确定后续方向与验收口径。P0-P2 对应的 M1-M9 已按批次 A-D 落地；
> M10-M14 保持触发式，不纳入本轮默认范围，也不表示当前版本已经发布。

## 1. 结论先讲

Magpie 的体量远大于 openllm。它同时做 Agent 配置管理、订阅登录、GitHub Copilot
等账号桥接、本地全能网关、路由组、插件、桌面界面、远程网关和同步，完整照搬会破坏
openllm 当前“单二进制、单实例、自托管、可离线”的定位。

真正值得借鉴的是它处理上游可用性的几个思路：

1. **先判断错误属于谁**：请求内容、模型能力、上游密钥、账号额度、提供商网络故障
   是不同故障域，不能用同一种冷却处理。
2. **额度不是布尔值**：同一上游 Key 可能同时受 5 小时、周、月和余额限制，且模型
   还可能单独限额。路由应读取“生效窗口”，并坚持 `unknown != exhausted`。
3. **限流应有 sink，不应一律长时间冷却**：仍有额度但暂时 429 的目标应排到队尾，
   稍后再试，而不是当成故障长期隔离。
4. **所有候选都忙时可以有限等待**：仅在尚未向客户端发送任何响应字节、且错误属于
   短暂忙碌时，按路由级预算等待并重排，不能让等待默认污染所有请求。
5. **会话粘性应服务于缓存收益**：粘性是优先信号，不是硬绑定；故障、饱和和额度耗尽
   必须立即打破。

因此建议路线是：

| 顺序 | 阶段 | 目标 | 结论 |
| --- | --- | --- | --- |
| 1 | 高可用内核 | 更准确地隔离故障域，接入真实额度状态，降低 429 和无效重试 | 优先做 |
| 2 | 运维效率 | 让路由决策、额度新鲜度、Key 轮换和模型变更更容易解释与维护 | 次优先 |
| 3 | 扩展能力 | 策略化中间件、媒体端点、远程上游、MCP 工具 | 按触发条件做 |
| 4 | 产品边界 | Agent 配置托管、订阅桥接、桌面端和动态插件运行时 | 不建议做 |

## 2. Magpie 功能概览

Magpie 不是一个单纯的反向代理，而是围绕本地 Agent 工作流构建的整套控制面。

| 层次 | Magpie 能力 | 对 openllm 的参考价值 |
| --- | --- | --- |
| Agent 接入 | 改写 Codex、Claude Code、Gemini CLI、OpenCode 等 Agent 配置；Profile 一键切换 | 低，openllm 定位是网关，不是 Agent 配置管理器 |
| 上游接入 | API Key、订阅账号、OAuth、插件账号、本地模型、自定义兼容端点 | 中低，订阅和账号桥接不应进入当前边界 |
| 协议网关 | Chat Completions、Responses、Anthropic Messages、Gemini 互转 | 中，openllm 已有 OpenAI 与 Anthropic 双向转换，可扩展更多端点 |
| 路由组 | 普通成员、嵌套组、Smart/Order/Rotate/Usage/Pace/Weight 策略 | 高，其中额度感知和错误域隔离最值得借鉴 |
| 额度 | 余额、5 小时/周/月窗口、账号级和窗口级上限、模型级额度 | 高，是当前最明确的缺口 |
| 会话 | 会话 ID、原生会话头、粘性、缓存收益、会话用量和恢复 | 高，openllm 已有 v1，可升级为缓存感知 v2 |
| 故障处理 | 同目标重试、跨候选切换、429 sink、有限耐心、拒绝分类、半开探测 | 很高，应优先吸收 |
| 可观测 | 路由决策轨迹、逐次尝试、用量、缓存、上下文占用、限流状态 | 高，可补 openllm 缺少的最近路由轨迹 |
| 中间件 | JS `onRequest`、`onEvent`、`onResponse`，模型映射、参数改写、敏感词等 | 中，借鉴能力，不建议引入动态 JS 运行时 |
| 工具 | Web Search、Vision 作为 MCP 服务，图片/视频生成 | 中低，属于产品扩展，不是网关稳定性核心 |
| 运维 | 加密备份、WebDAV/S3/GitHub 同步、配置导入、远程网关 | 中，先借鉴可靠性规则，跨机同步按需再做 |
| 桌面与插件 | 菜单栏、GUI、TUI、Web、Bun/OpenCode 插件生态 | 低，和 openllm 定位不符 |

## 4. 设计原则

所有后续功能都遵守以下约束：

1. **高可用优先**：先让故障隔离、额度判断和限流处理正确，再做便利功能和界面扩展。
2. **不改变默认路由语义**：新增调度策略和等待行为必须显式开启。`priority` 等现有策略
   的行为保持稳定。
3. **不再引入 `auto/*`**：不恢复 auto 路由，也不照搬 Magpie 的意图路由和自动组路由。
   模型别名和路由组组合必须显式配置。
4. **慢首字只影响延迟优先策略**：现有边界保持不变，不能扩大到默认策略。
5. **未知不等于耗尽**：额度读取失败、字段缺失、时间已过期时，状态是 `unknown`，
   只能保持中性或被真实故障排除，不能永久禁止候选。
6. **额度判断不能阻塞请求路径**：额度刷新在后台或管理接口执行；请求路径只读内存快照。
7. **不保存请求正文**：路由轨迹、额度和故障状态只保存协议字段、状态、时间、Token、
   哈希和原因，不保存提示词、响应或工具参数。
8. **保持零新增运行时依赖**：继续使用 Rust 标准库、现有 HTTP 客户端和 SQLite；不引入
   Redis、Node.js、Bun、WASM 或外部中间件。
9. **单实例边界不变**：同一 SQLite 文件仍只允许一个进程服务。

## 6. 高可用功能详案

### M1 故障域与重试分类

**问题**

当前 openllm 已能区分提供商熔断、模型冷却、上游 Key 冷却和部分 429/认证错误，但
“是否应该重试、是否应该冷却、冷却哪个对象”仍主要按 HTTP 状态判断。以下情况会混淆：

- 一个模型的上下文限制或推理字段不兼容，被当成提供商故障。
- 一个 Key 因余额耗尽返回 401/403/429，被当成所有 Key 都不可用。
- 内容策略拒绝可以换候选重试，但不应冷却任何凭证或模型。
- 某模型不在当前套餐，不应把整个提供商熔断。
- 429 可能只是短时 RPM，也可能是计划额度耗尽，二者应有不同恢复策略。

**方案**

引入统一的请求结果分类：

| 字段 | 取值 |
| --- | --- |
| `scope` | `transport`、`provider`、`credential`、`model`、`endpoint`、`request_shape`、`request_content`、`client` |
| `retry` | `same_target`、`next_target`、`wait_then_retry`、`do_not_retry` |
| `rest_ttl` | 建议隔离时间；无隔离时为 0 |
| `reset_at` | 已知额度恢复时间，可为空 |
| `confidence` | `exact`、`inferred`、`unknown` |
| `reason_code` | 稳定的机器可读原因，不依赖上游文案全文 |

分类规则：

1. 连接失败、DNS、TLS、读超时和 5xx 归入 `transport/provider`，继续走现有熔断。
2. 401/403 先识别认证、余额、套餐和内容策略。只有明确的凭证错误才冷却当前 Key；
   如果同一请求在第二个 Key 上得到同样结果，升级为 `provider` 或 `endpoint`。
3. 429 根据 `Retry-After`、额度响应体和已知额度快照区分：
   - 短时速率限制：`wait_then_retry`，只 sink 不长期冷却。
   - 计划额度耗尽且有可信 `reset_at`：`next_target`，当前窗口内排到最后。
   - 额度来源未知：短时 sink，按 `unknown` 处理，不永久隔离。
4. 明确的上下文超长、输出上限、模型不存在、套餐不含模型归入 `model`，只影响对应
   模型，不触发提供商熔断。
5. `thinking`、`reasoning_text`、工具 `strict`、图片格式、预填充等协议兼容错误归入
   `request_shape`。先按现有兼容层修复；再次失败则切换候选，不冷却凭证。
6. 内容策略拒答归入 `request_content`，允许切换候选，但默认不冷却任何对象。
7. 客户端自身取消、断连和错误请求归入 `client`，写 499/4xx 用量，不进入上游故障统计。

**控制台与诊断**

- `/api/routes/diagnose` 显示每个候选的最近故障域及原因。
- `/api/resilience/cooldowns` 增加 `scope`、`reason_code`、`confidence` 和 `reset_at`。
- 用量详情记录最终分类和是否建议重试，不保存错误正文全文。
- 新增指标：
  - `openllm_upstream_failures_total{scope,reason,retry}`
  - `openllm_failure_scope_transitions_total{from,to}`
  - `openllm_credentials_resting_total{provider,key}`（已有指标可扩展标签）

**验收标准**

- 同一 Key 的余额错误只冷却该 Key；第二个 Key 继续可用。
- 模型级 400/422 不增加提供商失败连续次数。
- 内容策略拒绝能切换候选，但不产生冷却记录。
- 客户端取消不增加任何上游熔断或冷却计数。
- 现有 429 `Retry-After` 透传测试全部保持通过。
- 错误分类逻辑全部有表驱动单测，且真实上游回复样本只使用脱敏后的固定片段。

### M2 上游额度快照与模型级窗口

**现状**

openllm 已能为 Command Code、OpenCode Go、DeepSeek 读取额度，也能展示部分模型额度，
但额度结果仍是管理页面的即时查询，没有统一快照，也没有进入路由评分。Provider quota
里的 5 小时、周、月、余额和模型额度没有共同的“当前是否受限、何时恢复”语义。

**目标数据模型**

新增持久化快照，请求路径只读内存缓存：

| 字段 | 含义 |
| --- | --- |
| `provider_id` | 提供商 |
| `provider_key_id` | 上游 Key；账号级额度可为空 |
| `model` | 模型级额度；空字符串表示提供商/Key 级 |
| `window_key` | `5h`、`daily`、`weekly`、`monthly`、`balance`、`custom` |
| `used`、`limit`、`remaining` | 读数，任一未知时允许为空 |
| `unit` | `token`、`request`、`usd`、`credit`、`percent` |
| `reset_at` | 窗口重置时间 |
| `source` | `provider_api`、`response_header`、`runtime_429`、`manual` |
| `confidence` | `exact`、`inferred`、`unknown` |
| `observed_at` / `valid_until` | 新鲜度窗口 |

从快照派生五个状态：

| 状态 | 条件 | 路由行为 |
| --- | --- | --- |
| `unknown` | 无数据、读取失败、字段不全、快照过期 | 中性，不排除 |
| `healthy` | 已知额度且低于低水位 | 正常评分 |
| `low` | 达到可配置低水位，例如 90% | 软降权，仍可尝试 |
| `exhausted` | 已知额度耗尽，且 `reset_at` 可信 | 有替代时排除，无替代时给出明确恢复时间 |
| `reset_due` | `reset_at <= now` | 触发刷新，暂不继续判定耗尽 |

多个窗口同时存在时，按“生效窗口”判断：

1. 已耗尽且恢复最晚的窗口优先决定返回时间。
2. 没有耗尽时，使用已用比例最高的窗口作为压力值。
3. 模型级窗口只影响对应模型；只有全部模型的额度都耗尽时，才升级为 Key/提供商级。

**额度如何获取**

按可靠性从高到低接入：

1. **提供商 API**：扩展现有适配器。每种上游单独实现、单独测试，不从 HTML 页面猜测。
2. **标准响应头**：只解析语义明确的 `x-ratelimit-*`、`anthropic-ratelimit-*` 等字段；
   无法确认单位或窗口时标为 `unknown`。
3. **运行时 429/402/余额错误**：可作为短期推断，但不能把单次 429 永久写成额度耗尽。
4. **人工登记**：允许为每个上游 Key 配置账号级和模型级的固定上限、周期与重置时间。
   这是最后兜底，也是新提供商最安全的起点。

刷新策略：

- 管理页手动刷新一次只影响一个 Key/提供商，避免并发轰炸。
- 后台刷新按提供商设置最短间隔，默认不启用。
- 缓存快照的新鲜度默认 15 分钟；余额和 5 小时窗口可更短，月窗口可更长。
- 重置时间已过时先刷新，不直接把旧读数继续当成耗尽。

**验收标准**

- 5 小时窗口耗尽但周窗口正常时，能够只在未来数小时内降权该目标。
- 模型 A 耗尽不影响同 Key 的模型 B。
- 所有模型都耗尽时才排除整个上游 Key。
- 额度读取失败、旧数据过期和重置时间已过均不会误判为耗尽。
- `unknown` 候选在诊断里显示“未知”，不是“不可用”。
- 刷新失败不覆盖上一个仍在新鲜度窗口内的可用读数，也不会阻塞普通请求。

### M3 `quota_paced` 额度感知路由

**借鉴点**

Magpie 的 `smart` 偏向“最早重置的额度先用完”，`pace` 偏向“按重置前每小时剩余额度
消耗”。两者都建立在真实额度窗口上。openllm 不需要一次复制全部策略，先增加一个
明确、可解释的额度策略即可。

**建议策略**

新增 `quota_paced`，规则如下：

1. 已知耗尽且在有效窗口内：有替代时排除，无替代时返回带有最早恢复时间的 429。
2. 未知额度：保持中性，不因为未知排到配置顺序之后。
3. 低水位目标：软降权，通常排在健康目标之后。
4. 都健康时优先比较“剩余额度 / 距重置小时数”，避免临近重置的少量余额浪费，也避免
   把仍有大量余额的账号过早打满。
5. 压力接近时使用现有会话粘性、成本、延迟和配置顺序作为次级因子。
6. 模型级窗口只参与对应候选的评分，禁止拿另一个模型的额度做代理。

`quota_paced` 只改变该路由的排序。未选择该策略的路由行为不变。

**诊断输出**

每个候选至少显示：

- 当前生效窗口和用于排序的窗口。
- `used/limit/remaining/unit`。
- 恢复时间、快照时间和新鲜度。
- 当前状态：`unknown/healthy/low/exhausted/reset_due`。
- 为什么被软降权、排除或保留。

**验收标准**

- 人工注入多窗口读数后，候选顺序稳定且可解释。
- 两个候选剩余比例相同但重置时间不同，排序符合定义。
- `unknown` 不会被无端降权；但没有可信数据时也不能声称“额度充足”。
- 现有 `priority`、`weighted`、`cost_optimized` 和延迟策略输出不变。

### M4 每上游 Key 的 RPM、并发与队列通道

**问题**

openllm 当前有提供商和模型级并发限制、队列等待以及网关访问 Key 的 RPM 限制，但没有
统一到每个上游 Key/账号的独立通道。多个 Key 限速不同、不同模型共用 Key、或某 Key
临时受限时，提供商级限制不够精确。

**方案**

为每个上游 Key 增加可选配置：

| 配置 | 作用 |
| --- | --- |
| `max_concurrency` | 该 Key 的最大同时请求数 |
| `requests_per_minute` | 滚动 60 秒请求上限 |
| `queue_limit` | 最多允许多少请求等待 |
| `queue_wait_ms` | 单个请求最多等待多久 |

请求候选顺序和容量判断先使用 Key 通道，再回落到提供商和模型级限制。等待期间：

- 如果另一个已就绪 Key 存在，优先切换，不等待。
- 仅当所有候选都因 Key 通道忙碌时，才按路由的等待策略处理。
- 客户端断开时释放排队位置。
- 排队不增加提供商失败计数。

**验收标准**

- Key A RPM 已满时，流量立即切到 Key B。
- 两个 Key 都满时，按配置等待或返回 429，错误带下一次可用时间。
- 并发计数在成功、失败、超时、取消和流中断时都正确释放。
- 不改变未配置 Key 通道的现有行为。

### M5 429 sink 与有界耐心等待

**借鉴点**

Magpie 把一个“仍有额度但暂时 429”的 Key/账号移动到队尾，而不是当成硬故障；当路由组
所有成员都暂时忙碌时，可在客户端尚未收到响应前等待、重排并再次尝试。

**Sink 设计**

Sink 是排序状态，不是冷却：

- 只有短时 429、明确是速率限制而不是额度耗尽时才进入 sink。
- sink 目标仍可被探测和成功请求唤醒。
- sink 期满后自动回到正常位置。
- 成功请求、配置变更和手动清除都可立即解除 sink。
- 指标单独区分 `sink` 和 `cooldown`，不能再混在一个状态里。

**有界耐心等待**

为路由增加可选配置，默认关闭：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `all_targets_busy_wait_seconds` | 0 | 所有候选暂时忙碌时的总等待预算 |
| `retry_jitter_ms` | 250 | 重试抖动，避免同时醒来 |
| `max_waiting_requests` | 小值 | 单实例同时等待上限 |
| `keepalive_during_wait` | 开启 | 流式客户端等待期间发送 SSE 心跳 |

只有同时满足以下条件才等待：

1. 还没有向客户端发送任何响应增量或状态。
2. 失败分类允许等待，例如短时 429、容量饱和、短暂 5xx。
3. 路由显式设置了等待预算。
4. 全局等待数量和等待时间没有达到上限。

认证失败、额度已知耗尽、内容拒绝、请求格式错误和客户端取消都不等待。

**验收标准**

- 默认配置下所有行为和当前版本一致。
- 路由开启等待后，短时忙碌可被吸收；等待结束仍失败时返回真实的上游错误。
- 任意候选中途成功，客户端只收到一次完整响应。
- 流式请求在等待期间有 keepalive，不会触发常见客户端空闲超时。
- 并发等待受全局上限保护，不产生重试风暴。

### M6 会话粘性 v2，缓存收益优先

openllm 已有会话 ID 和提示前缀粘性。下一版只做两个改进：

1. **粘性目标动态打破**：目标冷却、sink、额度低水位、额度耗尽、并发饱和或多轮失败时，
   立即允许切换。粘性永远不是硬绑定。
2. **缓存收益作为加分项**：使用近期 `cache_read_tokens`、`cache_write_tokens` 和命中率
   估计继续留在原目标的收益。没有缓存证据时，粘性只占普通优先级，不阻塞成本或延迟目标。

验收：

- 同一会话稳定落在同一健康目标。
- 原目标失败或饱和后，下一个请求能改绑，且诊断说明原因。
- 缓存命中的会话不会因为短期成本排序无意义地反复换目标。
- 不启用粘性时行为完全不变。

## 7. 运维功能详案

### M7 逐请求路由轨迹与尝试历史

**目标**

把现有“当前会怎么路由”的诊断扩展为“这次实际为什么这样路由”。Magpie 的 Routing
页面值得借鉴，但 openllm 不需要保存完整请求内容。

每个请求记录一条有上限的轨迹：

- 请求 ID、时间和路由 ID。
- 路由策略、会话粘性状态。
- 每个候选的顺序、eligible、deprioritized 和原因。
- 实际尝试的候选、状态码、耗时、首个 Token 时间、Token、费用和失败分类。
- 最终服务提供商、模型、Key ID 和回退次数。

不记录：

- 提示词、响应正文、工具参数和错误响应全文。
- 未经脱敏的上游请求头或响应头。

建议增加 `routing_traces` 和 `routing_attempts` 两张表，沿用现有用量保留策略；控制台
提供请求详情内的“路由轨迹”页签。数据量增长可通过只保留失败、回退、sink、熔断和
抽样成功请求控制。

验收：

- 每个回退请求能解释“上一候选为什么失败、下一候选为什么被选”。
- 轨迹不会保存请求正文。
- 删除或关闭轨迹功能不影响网关服务。
- 轨迹写入失败不影响请求主路径。

### M8 提供商端点与请求形状能力档案

**借鉴点**

Magpie 对 GLM Coding Plan、Zhipu 200 错误信封、DeepSeek reasoning 历史、Anthropic
参数拒绝、工具 `strict` 等做了按提供商和模型的能力学习。openllm 已有部分兼容处理，
但很多逻辑仍是单次请求内的兜底。

**方案**

为提供商、模型、端点建立小型能力档案：

| 能力 | 例子 |
| --- | --- |
| 认证方式 | `x-api-key`、Bearer、两者不能并存 |
| 端点变体 | 套餐端点与按量端点、Responses 与 Chat 的差异 |
| 推理历史 | 是否要求回传 `reasoning_content`、`reasoning_text` 或 thinking |
| 采样参数 | 是否接受 `temperature`、`top_p`、`top_k` |
| 工具参数 | 是否接受 `strict` |
| 错误信封 | 2xx 中包含错误对象、特定业务错误码等 |
| 上下文和输出 | 已由能力桶覆盖，继续复用 |

能力来源按优先级为：显式模板、管理员确认、一次运行学习。学习结果必须带版本或过期
时间，避免上游升级后永久沿用错误结论。

验收：

- 首次拒绝可按兼容规则重试一次，并持久化到有作用域的能力档案。
- 能力档案不跨提供商或模型错误传播。
- 模板版本变化时可重新验证或清除学习结果。
- DeepSeek、GLM、Kimi、严格工具字段等已有场景有回归测试。

### M9 模型自动纳入和 Key 生命周期加强

当前已有定时模型同步。可增加低风险的规则自动纳入：

- 按精确模型名、glob 或正则前缀选择新模型。
- 只新增，不删除已手动配置或禁用的模型。
- 同步失败时保留上一个有效目录。
- 规则变更记录审计。

Key 生命周期方面，openllm 已能在前端携带 Key ID 时原地替换 Secret。需要补齐的是：

- 明确保证替换后保留 Key ID、名称、顺序、健康历史、冷却和路由分配。
- 替换前复核使用该 Key 的配额池、访问 Key 限制和用量记录。
- 控制台显示“替换密钥”和“删除并重建”的语义差异。
- 审计日志只记录 Key 名称和 ID，不记录 Secret。

验收：

- 替换 Key 后历史用量仍能关联到同一 Key ID。
- 配额池和访问限制不丢失。
- 新 Secret 生效后旧冷却和健康状态按显式规则重置，控制台有说明。

### M10 加密配置包与可选远端同步

现有 `VACUUM INTO` 备份、配置导出/导入和恢复流程已经满足单机运维。只有在多台机器
运维同一套配置时，才建议借鉴 Magpie 的加密远端同步：

- 加密配置包不包含网关请求正文和使用明细。
- 支持本地文件，优先 S3 兼容存储；WebDAV 和 GitHub 按需求追加。
- 合并以版本哈希为准，冲突保留双方版本。
- 远端不可读、格式错误或解密失败时绝不覆盖本地。
- 同步范围明确区分配置、凭据和用量，默认不包含凭据。

暂不做全量双向同步和任意文件同步。

## 8. 扩展功能详案

### M11 声明式网关策略包

Magpie 的中间件能力值得借鉴，但动态 JS、Bun 或 WASM 会显著扩大攻击面和维护矩阵。
建议先提供少量内置、声明式策略：

| 策略 | 作用 | 默认 |
| --- | --- | --- |
| 模型别名 | 把客户端模型名映射到已有路由或模型 | 关闭 |
| 请求字段覆盖 | 设置、删除、移动或拒绝指定 JSON 字段 | 关闭 |
| 系统提示 | 按 Key、路由、模型添加固定系统提示 | 关闭 |
| thinking 清理 | 统一 `<think>` 或 reasoning 字段形态 | 关闭 |
| 敏感信息处理 | 复用现有防护，支持拒绝或遮蔽 | 关闭 |

每条策略必须：

- 有明确作用域和顺序。
- 在响应头或用量轨迹中标记已生效。
- 默认关闭。
- 不执行任意脚本，不加载外部包。
- 对结构化 JSON 使用解析器处理，不做字符串拼接。

### M12 Images、Audio、Batch 等端点

继续沿用 `EXTENSIONS.md` 的 E5：

- `images/generations`、`images/edits`
- 语音转写和语音合成
- Batch API
- 按需支持 Gemini 原生端点

主要风险是二进制响应、multipart 和内存上限，不是路由算法。先做一个端点族，一次验证
完整生命周期，再扩展。

### M13 OpenLLM 远端上游与路由组组合

可以借鉴 Magpie 的远端网关，但必须先确认产品是否真的要跨机器聚合。若做，建议：

- 一台 OpenLLM 作为另一台的显式 provider。
- 验证版本、协议、健康状态和鉴权。
- 远端故障映射为本地 `provider` 故障，不传递远端内部冷却。
- 禁止递归引用和环。

路由组组合的成本主要在解释和排障。只有出现“组合复用”真实需求时再做，且必须附带
环检测、最大深度和诊断展开。

### M14 Web Search/Vision MCP

Magpie 的搜索和视觉 MCP 是产品能力扩展，不是网关稳定性核心。若以后要做：

- 单独配置搜索提供商、预算、代理和 Key。
- 搜索与主路由共用费用记录和预算，但不共用自动降级。
- 图片只做透传或调用明确的视觉模型，不在网关保存原图。
- MCP 工具必须有独立鉴权、超时、体积限制和审计。

## 9. 明确不建议借鉴

| 项 | 不做的理由 |
| --- | --- |
| 订阅账号登录、OAuth、Keychain 读取和 Agent 凭证桥接 | 与网关定位偏离，涉及供应商条款、凭证托管和跨平台安全边界 |
| 修改 Codex、Claude Code 等 Agent 配置及漂移修复 | openllm 不是 Agent 配置管理器 |
| 每日预热、自动签到和领取订阅额度 | 依赖具体供应商条款，副作用和封禁风险高 |
| 动态 JS、Bun、WASM 插件运行时 | 扩大攻击面、依赖和兼容矩阵；先用声明式策略满足需求 |
| 桌面托盘、菜单栏和完整 GUI 壳 | 当前嵌入控制台已满足单实例运维 |
| 免费额度目录和全网提供商目录自动抓取 | 数据易过期，准确性无法保证 |
| 意图路由，用小模型自动决定强模型/便宜模型 | 成本和结果不稳定，容易形成不可解释的黑盒 |
| 全量复制 Magpie 的路由策略和嵌套组 | 策略数量不等于可用性，优先解决额度、故障域和限流 |
| 语义缓存 | 跨租户正确性和隐私风险高，继续保留精确缓存候选的结论 |
| 多实例共享 Redis 状态 | 破坏当前单实例、单二进制、单 SQLite 前提 |
| 对未命中的上游做 MITM 或绕过供应商客户端限制 | 与显式配置和安全模型冲突 |
| 默认开启全路由耐心等待或慢首字降权 | 会改变现有调用语义，必须按路由显式开启 |

## 11. 建议实施批次

### 批次 A：故障域和测试基线

交付 `M1`：

- 统一的 failure classification 结构和稳定原因码。
- 现有熔断、模型冷却、Key 冷却接入新分类。
- 诊断、指标和表驱动测试。
- 不新增配置，不改变健康请求路径行为。

这一批完成后，应能回答“当前错误究竟该冷却谁”，这是后续额度、sink 和耐心等待的基础。

### 批次 B：额度快照和额度策略

交付 `M2 + M3`：

- 统一额度快照表、后台刷新和内存缓存。
- 先覆盖已有 Command Code、OpenCode Go、DeepSeek，再按实际使用增加适配器。
- 支持人工登记的 Key/模型/窗口额度。
- 新增 `quota_paced`，仅在显式选择时生效。

完成后，用户可以直接看到每个 Key、每个模型的额度状态、恢复时间和路由排序原因。

### 批次 C：限流与忙碌恢复

交付 `M4 + M5`：

- 每上游 Key 通道限制。
- 429 sink。
- 按路由开启的有界耐心等待和 SSE keepalive。
- 严格的全局限流，防止等待放大为请求风暴。

完成后，短时限流和资源竞争应主要被网关内部吸收，而不是直接落到 Agent。

### 批次 D：运维可解释性

交付 `M6 + M7 + M8 + M9`：

- 缓存感知会话粘性。
- 逐请求路由轨迹。
- 端点与请求形状能力档案。
- 模型自动纳入和 Key 生命周期加强。

### 批次 E：扩展能力

只有需求明确时才依次评估：

1. `M10` 加密配置包和远端同步。
2. `M11` 声明式策略包。
3. `M12` 媒体和 Batch 端点。
4. `M13` 远端 OpenLLM 上游。
5. `M14` Web Search/Vision MCP。

## 12. 跨功能验收清单

每个批次至少验证以下事项：

| 类别 | 验收点 |
| --- | --- |
| 语义 | `unknown != exhausted`，未知额度不会被排除 |
| 隔离 | 单 Key、单模型、单请求形状的错误不会错误升级为提供商熔断 |
| 默认值 | 未配置新策略时，请求顺序、重试次数和冷却时间与 v0.3.25 基线一致 |
| 性能 | 普通请求路径不增加同步网络调用或每请求 SQL 查询 |
| 并发 | 请求取消、超时、流中断和进程关闭时，所有租约和队列都能释放 |
| 持久化 | 冷却、sink 和额度快照重启后可恢复；过期状态不会永久生效 |
| 隐私 | 轨迹与快照不记录提示词、响应正文、工具参数和 Secret |
| 可解释 | 诊断能说明候选被保留、软降权或排除的具体原因 |
| 可运维 | 所有新增状态有指标、日志、审计或控制台入口 |
| 兼容 | 旧数据库迁移可回滚，旧配置无新字段时按原语义读取 |
| 平台 | Windows、Linux、macOS 测试通过；定时和时间测试不受时区影响 |
| 边界 | 不引入 `auto/*`，不默认启用慢首字降权，不引入动态插件运行时 |

## 13. 第一轮建议

第一轮只做 `M1`，并在同一轮为 `M2` 定义数据模型和测试夹具，不直接实现额度调度。

原因：

- 当前最危险的不是缺少更多策略，而是错误被作用到错误的故障域。
- 额度策略依赖稳定、可解释的 failure scope 和 reset 语义。
- sink、耐心等待和会话粘性 v2 都依赖同一套“哪些失败可以再试”的判断。

第一轮完成后，再决定 `M2` 首先接哪些上游额度适配器。这样可以把“模型级额度怎么获取”
拆成可逐个验证的提供商适配器，而不是加入一个无法证明准确性的通用猜测逻辑。
