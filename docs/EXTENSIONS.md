# 扩展功能候选与取舍结论

> **本文档只给结论，本轮不实现任何候选功能，也不改动任何代码。** 它是阶段三的交付物，用于把「下一步可以做什么、为什么现在不做」讲清楚，供后续排期决策使用。
>
> 落地后的状态会同步回下面的「结论速览」与条目正文（目前 E1 已交付），其余条目仍保持评估时的口径。
>
> 评估基准：openllm v0.3.14（阶段一高可用加固与阶段二运维能力交付之后）。参照项目：`~/code/OmniRoute-release-v3.8.52`（下文简称 OmniRoute）。

## 1. 评估口径

当前架构的硬前提（所有候选都在这个前提下评估）：

- **零新增运行时依赖、单二进制**：控制台已嵌入二进制，除 SQLite 外不引入外部中间件。
- **单实例、单数据库文件**：SQLite 单写者，网关会拒绝第二个实例共享同一数据库（见 `OPENLLM_MULTI_INSTANCE`）；熔断/冷却/配额窗口状态在进程内，并异步镜像到 SQLite。
- **请求路径上的语义不可削弱**：准入与内存保护、排空、熔断与冷却、配额池公平分配、可解释路由评分都不能为了新功能退化。

每个候选按以下维度评估：

| 维度 | 含义 |
| --- | --- |
| 收益 | 对可用性 / 成本 / 运维效率 / 兼容性的实际影响，不按功能数量计 |
| 成本 | 实现 + 测试 + 文档的粗略人日区间（含验证脚本） |
| 依赖 | 是否需要新的运行时依赖、外部服务或新基础设施 |
| 风险 | 正确性、隐私、成本放大、与现有语义冲突 |
| 结论 | 做（排期）/ 待定（附触发条件）/ 不做（附理由） |

## 3. 详细评估

### E1 控制台配额池管理界面 —— 做（P0）

- **状态：已交付。** 控制台新增「配额池」页（`/pools`），可创建、编辑、启用/停用和删除池，直接编辑每个密钥的权重与策略，并显示每个池的实时用量、饱和状态与拒绝次数。本节其余内容保留为当时的评估记录。
- **现状**：提供商配额池的读写接口（`/api/provider-pools`、`/api/provider-pools/{id}`、`GET /api/providers/{id}/pool-usage`）已完整实现并有 13 项单测；`/metrics` 导出 10 个池指标；「诊断」页能**看**池用量。但控制台没有任何地方可以**创建或修改**池与权重分配，配置只能靠直接调 API 或导入配置文件。
- **收益**：这是本清单里唯一「后端能力已存在、只缺一个入口」的项。补齐后配额池从「需要看文档才能用」变成开箱可用。
- **成本**：1–2 人日（表单一页 + 校验回显 + 用量列；样式与现有 Providers/Keys 页一致）。
- **依赖与风险**：无新依赖。唯一风险是权重校验（1–100、策略枚举、同一密钥不重复）必须与后端 `normalize_pool` 保持一致——直接复用后端报错即可，无需前端另写一套规则。
- **契合度**：完全契合；不触碰请求路径。

### E2 会话 / 提示前缀粘性 —— 已交付

- **状态：已交付。** 除 `priority` 外，路由按网关访问密钥、路由和会话作用域记录一个 TTL 目标；显式会话 ID 优先，缺少会话 ID 时使用首个用户消息与系统提示的稳定前缀哈希。`priority` 每次按配置优先级和可用性选择，不读取、续期或改绑已有粘性记录，首选恢复后重新优先尝试。其他策略的粘性只移动健康且未饱和的候选，目标冷却、饱和、熔断或移除时会自动改绑。映射默认 30 分钟滑动 TTL、10,000 条上限，并可选同步到 SQLite；镜像失败只降级为纯内存，不阻断请求。启用粘性的策略在路由诊断中显示 `session` 因子，`/metrics` 导出条目、命中、未命中、改绑、淘汰和镜像错误。

- **当时的现状**：`usage_logs.session_id` 已经在记录会话，容量感知路由的评分里对加权/轮询策略也已经有 `session_affinity` 这个因子名，但路由器并不真的按会话固定目标；本轮已补上。
- **收益**：把同一会话稳定落到同一上游，可以显著提高上游 prompt cache 命中率（Anthropic/OpenAI 的缓存命中直接体现为成本与 TTFT 下降）。这是 LLM 网关里性价比最高的优化之一。
- **成本**：4–6 人日（会话→目标映射（进程内 + 可选持久化）、TTL 与容量上限、与容量/熔断的交互、指标与诊断展示）。
- **依赖与风险**：无新依赖。风险是与现有「容量优先」语义冲突：粘性目标饱和或刚失败时必须**立即**打破粘性（粘性只做排序偏好，不能阻止故障转移，也不能让请求排队）。建议实现为「在 `order_targets` 的稳定次级排序上，以会话记忆在健康且有余量的目标间提权」，与现有「容量/健康优先」的重排逻辑同一层。
- **契合度**：高。可复用 `TargetAssessment`/`deprioritized` 机制与 `/api/routes/diagnose` 的候选理由输出（新增一个 `session` 因子即可）。

### E3 精确匹配响应缓存 —— 做（P1，默认关闭）

- **现状**：没有任何响应缓存；只有上游返回的缓存命中计数（`cache_read_tokens` / `cache_write_tokens`）被记录与展示。
- **收益**：对重复请求（评测、回归、同一提示反复调用的内部工具）可以完全省掉上游成本与延迟。
- **成本**：5–8 人日（缓存键设计、存储与 TTL、配额与磁盘上限、命中指标、控制台开关与清理入口）。
- **依赖与风险**：无新依赖（SQLite 表 + TTL 即可）。风险集中在正确性与隐私：必须按 **访问密钥作用域**（默认不跨 Key 共享）、按模型与上游目标、按影响输出的参数（temperature、tools、response_format、流式与否）严格生成缓存键；带 `Authorization` 之外的私有字段、图像/多模态与工具调用默认不缓存；命中必须写回与真实请求一致的用量字段（标记 `cached`）以免预算与统计被扭曲。默认关闭，且要求显式设置作用域才启用。
- **契合度**：中高。可复用现有用量记账与请求日志链路；但要在「重试/降级」循环之外单独一层，避免与流式恢复语义互相纠缠。语义缓存（embedding 相似度）不建议同时做：模糊命中带来的正确性与跨租户风险远高于收益。

### E4 告警通道扩展 —— 不做

- **状态**：内置 Webhook 与聊天渠道投递已移除；旧数据库表和历史迁移保留以兼容升级，旧配置中的相关项导入时明确跳过。
- **替代路径**：由随附的 Prometheus 告警规则与 Alertmanager 负责通知、去重、分组和静默，网关仅负责指标、运行状态与请求诊断。

### E5 更多上游端点透传（images / audio / batch）—— 做（P2）

- **现状**：`/v1/chat/completions`、`/v1/completions`、`/v1/responses`、`/v1/embeddings`、Anthropic `/v1/messages` 与 `/v1/messages/count_tokens` 都已支持（含跨协议双向转换），但图像生成、语音转写/合成、Batch API 没有入口。
- **收益**：让网关覆盖「同一套密钥与配额」的全部常用端点，避免用户为了图像/语音再配一套直连。
- **成本**：2–4 人日（每个端点主要是路由 + 透传 + 用例记账；图像/音频响应的缓冲上限需要单独设值）。
- **依赖与风险**：无新依赖。风险是二进制响应的内存占用与错误形态不一致，需要沿用 `OPENLLM_MAX_UPSTREAM_BODY_MIB` 的缓冲保护并给错误响应留出可读路径。
- **契合度**：高，是现有策略的延伸；但收益取决于使用方是否真的需要这些模态，因此排在 P2。

### E6 上游配额遥测与配额感知调度 —— 待定

- **现状**：配额池（网关自己的窗口账本）与 `GET /api/providers/{id}/quota` 已存在；OmniRoute 的卖点之一是把「提供商侧剩余额度」纳入调度，并明确区分 `healthy / approaching_limit / exhausted / unavailable / unknown`，**where unknown ≠ exhausted**。
- **收益**：对按额度（而非按限流）计费的免费额度或包月账户，可以把请求提前导向仍有余额的上游，而不是等 429 才发现。
- **成本**：6–10 人日（额度来源接入：响应头解析、主动探测、手工登记；额度状态机；评分因子；诊断呈现）。
- **依赖与风险**：**关键依赖是额度信息的可靠性**。上游几乎不统一暴露剩余额度，靠猜会把可用上游误判为耗尽——而这正好是现有路由刻意避免的错误（未知一律按中性因子保持可选）。因此结论为待定。
- **触发条件**：出现「主要按额度计费、且额度可被可靠读取（响应头或查询接口）」的上游，或运维方愿意手工登记额度时再做。

### E7 用量计费与账单导出 —— 做（P2）

- **现状**：请求级成本（`estimated_cost_micros`）、按密钥的日预算/日 token 上限、生命周期累计用量都已入库；导出只有请求日志 CSV。
- **收益**：把「谁用了多少、该收多少」变成一条可交付给财务/团队的材料（按密钥或租户的周期账单），并支持「接近预算」提醒。
- **成本**：3–5 人日（按周期聚合、账单 JSON/CSV 导出、预算阈值告警事件、控制台呈现）。
- **依赖与风险**：无新依赖。风险是价格数据缺失导致的低估——必须延续现有口径：`unpriced_requests_total` 明示「未计价请求数」，账单不得把未知价混进总额而不标注。
- **契合度**：高，复用现有用量与成本链路。

### E8 上游错误细分分类 —— 做（P2）

- **现状**：已有「临时 4xx 先重试一次」「429 不参与同目标重试」「5xx/连接类先重试再切换」等分类，并会把最后一次 429 的 `Retry-After` 透传。
- **收益**：把认证失败、额度耗尽、上下文超长、内容策略拒绝这类**重试无益**的错误直接归类，给出可操作的错误信息（哪个密钥、哪个模型上限），避免无意义的同目标重试与冷却抖动。
- **成本**：1–2 人日。
- **依赖与风险**：无。风险是过度归类会把「其实是临时故障」的错误变成不重试——因此只做**明确的**分类（上游错误码/错误类型字符串），其余保持现有行为。
- **契合度**：高，改动集中在 `mark_*` 与错误映射处，有现成测试骨架。

### E9 多模态桥接 —— 待定

- **现状**：消息类协议之间的请求/响应互转已完整（含流式与 reasoning 透传），但**模态**层面的桥接（如把 OpenAI 的 `image_url` 块转成 Anthropic 的 `source` 块、音频输入输出转换）只覆盖了上游本来就接受的形态。
- **收益**：跨提供商使用带图请求时不必关心上游的图片表达方式。
- **成本**：8–12 人日（组合矩阵大：协议 × 模态 × 流式/非流式，每个组合都要有往返测试）。
- **依赖与风险**：无新依赖（不落盘、不改图）。风险是矩阵膨胀带来的长期维护成本，以及「转换后语义不等价」的静默降级。
- **触发条件**：出现实际需求（跨提供商图片请求失败成为常态）时，按「先做 OpenAI→Anthropic 图片块」单点起步。

### E10 提示压缩 / 历史摘要 —— 待定

- **现状**：无任何请求内容压缩。OmniRoute 把「RTK + Caveman 压缩」作为核心卖点（宣称平均省 ~89% token）。
- **收益**：直接降低上游成本，对长上下文与工具型代理流量收益最大。
- **成本**：8–14 人日（规则型压缩、可回退校验、压缩率与质量指标、与上游 prompt cache 的交互）。
- **依赖与风险**：规则型压缩无新依赖，但**语义损失不可逆**且会**降低上游缓存命中**（改写后的前缀不再命中），也可能破坏工具调用与 JSON 输出约束。必须默认关闭、按模型/密钥白名单开启，并明确告知调用方（响应头标注已压缩）。
- **触发条件**：先用量数据证明「上下文长度是主要成本来源」，并有一个可接受的压缩率/质量评估口径。

### E11 多管理员与 RBAC —— 待定

- **现状**：单个 `OPENLLM_ADMIN_TOKEN`（未设置即管理接口开放），审计日志记录动作但不记录操作者身份（统一为 `admin`/`local`）。
- **收益**：多人运维时能区分「谁改了什么」，并限制只读角色的写权限。
- **成本**：5–8 人日（管理员表与口令哈希、会话/令牌、角色校验中间件、审计记录操作者）。
- **依赖与风险**：无新依赖，但会引入「认证是网关自身职责」的长期负担（口令策略、锁定、重置流程），与当前「把鉴权交给反向代理/私网」的定位相冲突。
- **触发条件**：出现必须区分操作者的合规要求，或外包/多团队共同运维同一实例。

### E12 访问密钥策略增强 —— 做（P2）

- **现状**：密钥级策略已有模型白名单、日 token/成本上限、每分钟请求数、并发上限、路由策略与过期时间。
- **收益**：补齐「从哪来」（IP/CIDR 白名单）与「什么时候能用」（时段/工作日），缩小密钥泄漏后的爆炸半径。
- **成本**：2–3 人日。
- **依赖与风险**：无依赖。风险是引入反向代理场景下的真实客户端 IP 取值问题——必须只信任显式配置的代理层（例如仅在设置了「信任的代理」时才读取 `X-Forwarded-For`，否则用连接来源地址），否则白名单形同虚设。
- **契合度**：高，属于现有密钥模型的字段扩展。

### E13 OpenTelemetry 导出 —— 待定

- **现状**：Prometheus 指标 + 结构化日志 + 请求 ID 串联已能完成「指标定位 → 单条请求追踪」，但没有分布式追踪导出。
- **收益**：跨网关/上游的链路视图，以及在已有 OTel 栈的组织里统一观测。
- **成本**：6–10 人日（OTLP/HTTP + Protobuf 或 JSON 编码、span 生成点、采样与批量发送；若引入官方 SDK 则与「零新增运行时依赖」冲突，必须手写协议或只支持 HTTP/JSON）。
- **依赖与风险**：依赖冲突是主要风险（需要手写编码，长期维护成本高）；其次是追踪采样在高并发下的额外开销。
- **触发条件**：运维方已有 collector 且明确要求追踪；否则继续用 Prometheus + 日志。

### E14 请求体流式转发 —— 待定

- **现状**：网关**整体缓冲**请求体（这是准入字节预算与内存保护的实现基础，也是超过 `OPENLLM_MAX_BODY_MIB` 直接拒绝的原因）。
- **收益**：超大请求（长文档、批量图像）不再需要整体进内存，降低内存峰值。
- **成本**：6–10 人日。
- **依赖与风险**：风险高且集中在语义：现有「按字节记账 → 超预算拒绝」的提前拒绝、请求重试（需要重放请求体）、跨协议转换（Anthropic↔OpenAI 需要解析整个 JSON）都依赖完整请求体。要保留这些语义，就得先落地「可重放的流式缓冲」或按端点区分策略，属于对核心路径的改造。
- **触发条件**：出现真实的大请求内存压力事件，且现有 `OPENLLM_MAX_INFLIGHT_REQUEST_MIB` 无法缓解。

### E15 路由策略扩展 —— 做（P2）

- **现状**：6 种策略（priority、weighted、round_robin、cost_optimized、latency_optimized、least_used），评分框架已有 8 个因子与可解释输出。
- **收益**：更贴合真实运维目标，例如「按 P95 延迟择优」而不是平均延迟、成本×延迟混合权重、按配额余量择优。
- **成本**：2–4 人日/策略（含控制台选项与诊断理由）。
- **依赖与风险**：低。风险仅是策略过多导致行为难解释——因此每个新策略必须复用现有因子与 `/api/routes/diagnose` 的逐项理由，不新增隐式行为。
- **契合度**：高，是评分框架的自然扩展。

### E16 MCP / 工具聚合网关 —— 待定

- **现状**：网关会探测上游的 `tool_search` 兼容性并自动移除不兼容工具，但没有工具层聚合（多个 MCP server 合并成一个工具集、工具级路由）。
- **收益**：客户端只连网关就能用上全部工具。
- **成本**：10+ 人日（协议实现、工具命名空间与冲突、鉴权、超时与流式事件）。
- **依赖与风险**：安全边界大（工具执行权限）、协议演进快，与「稳定的小网关」定位偏离。
- **触发条件**：内部明确以网关作为工具入口的标准形态。

### E17 请求改写（系统提示注入、参数钳制、模型别名）—— 待定

- **现状**：已支持模型前缀、路由匹配、能力上限向下兼容；但没有内容层面的改写。
- **收益**：统一注入组织级系统提示、统一钳制温度/最大输出、把外部模型名映射到内部别名。
- **成本**：3–5 人日。
- **依赖与风险**：无依赖，但**透明性**是前提：任何改写都必须在响应头或日志中标注，且默认关闭（否则调用方看到的响应与请求不再对应，排障困难）。
- **触发条件**：出现「必须统一约束调用方参数」的运维要求。

## 4. 本轮明确不做

| 编号 | 候选 | 不做的理由 |
| --- | --- | --- |
| D1 | 多实例共享状态（Redis 软依赖：限流、认证缓存、配额、预热熔断器） | 与已确认的部署前提冲突：SQLite 单写者、单实例、零新增运行时依赖。引入 Redis 会把「一个二进制 + 一个文件」变成需要运维的分布式系统，并让熔断/冷却/配额语义在跨实例下变得难解释。若将来真要多实例，应先做的是把状态分层与一致性语义重新设计，而不是先加一个中间件。 |
| D2 | 插件 / 动态扩展系统（动态库、WASM 沙箱） | 与「零依赖单二进制、可审计」冲突；动态加载会同时扩大攻击面与支持矩阵。扩展需求优先通过管理 API、Prometheus 指标与外部进程满足。 |
| D3 | 桌面端 / Electron 客户端 | 与网关定位无关（网关是被调用的服务，不是用户的编辑器）；控制台已内嵌在二进制中。 |
| D4 | 免费额度目录（聚合各家免费层的 token 预算） | 数据维护成本高、易过期，且对自托管/内网场景价值有限；且这类目录的准确性无法由本项目保证。 |
| D5 | gRPC / HTTP-2 上游、MITM 中间人代理 | 现有上游全部可用 HTTP/JSON 覆盖；MITM 代理与「显式配置的上游」安全模型冲突。 |
| D6 | 语义（相似度）缓存 | 见 E3：模糊命中的正确性与跨租户风险高于收益，先做精确匹配缓存。 |
| D7 | 19 种路由策略「全量对齐」OmniRoute | 策略数量不是价值；每个新增策略都会增加解释成本。按 E15 的方式按需增补，并保持可解释输出。 |

## 5. 建议优先级与触发条件

1. **已完成（P0）**：E1 控制台配额池管理界面——后端已具备，缺的入口现已补齐（控制台「配额池」页）。
2. **近期（P1）**：E2 会话/前缀粘性 → E3 精确响应缓存。两者都直接影响成本与延迟，且都不引入新依赖。E4 告警通道（聊天渠道部分）已完成。
3. **之后（P2）**：E5 端点透传、E7 计费账单、E8 错误细分、E12 密钥策略增强、E15 路由策略扩展。可穿插进行，每项都可独立交付。
4. **触发式（待定）**：E6、E9、E10、E11、E13、E14、E16、E17 —— 每项都在正文里写明了触发条件，达成条件再排期。
5. **不做**：§4。若部署模型或安全前提发生根本变化（例如明确要多实例或需要插件生态），应重新评估 D1/D2，而不是绕过它们。

## 6. 与参照项目（OmniRoute）的取舍说明

OmniRoute 是一个体量大得多的多租户 AI 网关（数百个提供商、免费额度目录、压缩、看板、桌面端、插件生态），它的很多能力建立在开放 SaaS 前提上（多实例、Redis、外部目录、Electron 前端）。openllm 的定位是**自托管、单二进制、单实例、可离线**，因此：

- **已经对齐的部分**：熔断与冷却、失败分类与有界重试、配额池的工作守恒公平分配、配额状态区分「未知 ≠ 耗尽」、零上游请求的路由预览/诊断、结构化自检与快照导出、可观测性产物（规则 + 看板 + 校验脚本）。这些在阶段一/二已交付。
- **值得后续借鉴**：配额遥测（E6）、提示压缩（E10）、多模态桥接（E9）、更丰富的策略（E15）——但都要按本文的触发条件评估，而不是为了「功能对齐」而实现。
- **刻意不借鉴**：多实例共享状态（D1）、插件生态（D2）、桌面端（D3）、免费额度目录（D4）。
